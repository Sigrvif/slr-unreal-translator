SLRUnreal

The SLRUnreal is an addon that adds a new game engine to SLR Translator, so Unreal Engine games (UE4/UE5) can be translated the same way RPG Maker games are: with the DSLR translation engine, glossaries and SLR's QC pipeline. It reads the game's containers (.pak and .utoc+.ucas) directly, extracts every Japanese string with its asset context, and writes translations back with length-aware patching. It ships its own Python backend and runtime, so nothing extra has to be installed. The game itself is never modified — export produces rebuilt containers you apply to a copy of the game.

This page is shipped by the addon (its docs field in package.json — see Shipping a documentation page). The same content also travels inside the addon as assets/help.html for SLR builds without the addon documentation system.

What this addon does

  • Find every translatable string in the game's containers. The scan walks the pak index and the IoStore table of contents, parses each package (legacy and Zen formats), and extracts FText and FString strings — dialogue tables, widget text, quest and item names — with the owning asset, object and property path as row context. On IoStore (Zen) games the scan also collects each package's name-table strings that carry Japanese: some engines display raw names as UI text (SampleGameA's options menu is DataTable row keys). Because a name table mixes display labels with internal identifiers (animation names, component names, asset paths), those rows arrive pre-tagged: yellow (usually safe — check, then translate) or red (structural identifier — leave alone unless you know the game), and both are skipped by batch translation until you promote them. A name is red when it matches structural patterns (Blueprint/compiler prefixes like K2Node_, generated suffixes like _GEN_VARIABLE, GUID tails), contains a path, or — the exact rule — is itself a game asset file name (e.g. a BGM cue like 1_短くドビュ_Cue: renaming it would break every sound reference), carries a numbered variant tail (_001, _001_L — mesh bones, material slots, morph targets), or is shared across many packages (sockets, morph/animation switch names replicated everywhere). Rows that are NOT name-table strings (ordinary FText dialogue/UI text) stay untagged — safe by construction. Games whose pak index is AES-encrypted are supported: the key is discovered offline from the game's own executable (the encrypted index validates every candidate, so a found key is cryptographically confirmed — no key is ever bundled with the addon, and the confirmed key is cached in the addon folder's backend/keys.json).
  • Translate as a normal SLR project. One entry per asset, one row per string, in table order; contexts from the scene graph (asset → export → property path). Blank translations are never written into the game.
  • Unreal-aware translation patterns. While an Unreal project is the open project, the DSLR engine automatically translates with Unreal text-protection patterns instead of its RPG Maker ones — no manual pattern clearing, no second engine setup (see Unreal translation patterns below). Your DSLR settings are never modified.
  • Portable projects. Project creation also captures a staging set (every text-bearing package plus container metadata) into the project itself — Save Project packs it into the .slrproj, so the project is self-contained and exports need no game folder (the SLRUnity model). Measured cost: ~90 MB for a 3 GB game, because only text assets are captured.
  • Write translations back on export with length-aware patching: strings may grow or shrink; the exporter re-splices the payloads, updates every shifted offset up through the package and container structures, and verifies the result by re-reading it. By default the export is a tiny patch container (<name>_SLR_P.pak, or a <name>_SLR_P.utoc/.ucas pair on IoStore games) built entirely from the staging set — copy it into the game's Content\Paks folder beside the base containers, delete it to uninstall. The full-rebuild mode (original behavior, needs the game folder) remains available as an export option.
  • Swap image-overlay materials (demosaic) — a standalone operation with its own patch container: where a model binds the game's overlay material, the tool writes the clean material that ships in the same package instead. Run it from the project dialog's Demosaic (standalone) section (see Demosaic below).
  • Translate text drawn into images through a standalone SEP round-trip: extract every texture as PNG, translate the images in an SEP project, and write the rendered versions back into rebuilt containers (see Image translation below).
  • Replace the game's fonts — optional, in both flows that rebuild containers: the game's font files are swapped for SLR's own faces so translated English renders narrow and untranslated Japanese keeps rendering (see Fonts below).

Installing

Short version: extract the downloaded archive for YOUR platform (SLRUnreal--win.zip on Windows, SLRUnreal--linux.zip on Linux — each carries its own bundled Python) into www/addons/, then restart SLR Translator. The Oodle decompression library is not bundled (Epic’s license does not allow it): it is picked up automatically from the game being translated (most UE games ship it beside their executables) or from a local Unreal Engine install; an explicit path can be set via the SLRUNREAL_OODLE_DLL environment variable. To remove the addon, delete the SLRUnreal folder. See also Installing an addon.
  1. Find the addons folder: open your SLR Translator installation folder (the one containing SLR Translator.exe) and inside it www/addons/ (create it if it does not exist).
  2. Extract the archive into it: right-click the downloaded SLRUnreal--win.zip (for example SLRUnreal-1.0.1-win.zip) → Extract All (Windows opens .zip files by itself; a .7z needs 7-Zip or similar but is smaller), extracting INTO www/addons/. The package wraps everything in one SLRUnreal/ folder, so the result is www/addons/SLRUnreal/ directly containing package.json, UnrealAddon.js, lib/, backend/, runtime/, docs.html and assets/. Do not extract into an extra nested folder of the same name.
  3. Restart SLR Translator. The New Project dialog now shows a SLRUnreal entry (with its own icon) — pick it, then Select Folder and choose the game folder (or its *-Win64-Shipping.exe). UE games are detected automatically.
Linux: install SLRUnreal--linux.zip the same way. The addon translates Windows game copies on a Linux machine — point it at the game folder exactly as on Windows (the *-Win64-Shipping.exe is only READ as data for key discovery; nothing Windows actually runs). Export produces the same patch containers, which you then copy to wherever the game runs.
Removing / updating: delete (or replace the contents of) www/addons/SLRUnreal/ and restart. Your discovered pak keys live in backend/keys.json inside that folder — back it up before deleting if you want to keep them.

The workflow

  1. Create the project. New Project → SLRUnreal → Select Folder, then pick the game folder (or its *-Win64-Shipping.exe). Progress streams into the project-creation console; if the game needs a key you will see the offline discovery run (a few seconds per game). The result is a normal SLR project: one entry per asset, one row per string, with asset contexts in Row Properties.
  2. Translate. Everything standard SLR: glossary, DSLR batch translation, QC checks — with Unreal patterns applied automatically while the Unreal project is open. Leave rows blank to skip them — blank translations are never written into the game.
  3. Export. Export with mode Folder or Zip. The default export is a patch container built entirely from the project's staging set (portable — the game folder is not needed): a small <name>_SLR_P.pak (legacy pak games) or a <name>_SLR_P.utoc/.ucas pair (IoStore games). Copy the output into the game copy's Content\Paks folder beside the base containers and launch; delete the patch files to uninstall. Tick Full container rebuild in the export dialog to instead rebuild the complete containers from the original game folder (the pre-8a behavior). The summary reports rows patched, rows skipped and the verification result; if the game folder changed since project creation, a warning names what moved.

Unreal translation patterns

The DSLR engine ships with RPG Maker protection patterns — the regexes that keep \C[2]-style control codes, nameplate escapes and MV/MZ system messages out of the translator's mouth. None of that exists in Unreal text, and Unreal text has its own must-survive markup. The addon therefore switches the pattern sets automatically: while an Unreal project is the open project, DSLR's four pattern options (Protected, Aggressive Splitting, Isolation, Cutting Corners) resolve to Unreal sets at translation time. Open any other project — or none — and they resolve to your stored DSLR values, byte for byte. There is one DSLR engine and one setup; the addon never writes to your DSLR settings, and nothing needs restoring after a crash or restart.

  • Protected instead: rich-text markup (<Em>…</Em>, <font color=…>, <br/>), FText format arguments ({0}, {PlayerName} — Format() looks these up by name at runtime, so a translated-away argument breaks the string), and DSLR's own batch dividers.
  • Split away (not sent): empty lines and whole cells without Japanese (already-Latin UI labels cost tokens and risk re-translation).
  • Corners: filename-looking rows (including UE asset extensions), stray whitespace and linebreak padding.
  • Gone while an Unreal project is open: every RPG Maker-specific pattern (nameplate madness, MV/MZ/VX system-message translations, dialogue-plugin shapes) — the very ones you would otherwise clear by hand.

The settings: Options → General → SLRUnreal. The Use Unreal patterns while an Unreal project is open toggle (on by default) turns the switch off entirely — Unreal projects then translate with your own DSLR patterns completely unchanged. Below it sit editable copies of the four Unreal pattern sets (same editor and format as DSLR's pattern boxes: comma-separated regex literals, // comment lines). Small adjustments — an extra protection for a game-specific tag, dropping a split you don't want — go there, with no file editing; changes apply to the next translation, no restart. Clearing a box means no patterns at all for that family, exactly like clearing DSLR's own boxes (the built-in defaults ship in lib/uePatterns.js inside the addon folder if you want them back).

Where you see what: the DSLR options tab always shows your stored pattern sets — the switch is applied at translation time, based on the project that is open, and deliberately does not rewrite the settings view. If you previously cleared DSLR's patterns by hand for Unreal work, you can restore their defaults there for your RPG Maker projects; this addon never edits them.

Image translation (SEP round-trip)

Text drawn into images (UI screens, name plates, tutorials) is translated through SEP, SLR Translator's image editor — as a standalone round-trip, decoupled from the strings project. Both tools live on the addon's New Project slide.

  1. Extract images. New Project → SLRUnreal → Select Game Folder & Extract Images. Every game texture is decoded and written as a PNG into <Game>_unreal_img next to the game (plus a manifest.json). Nothing in the game is touched.
  2. Trim the folder. Delete the images you do not want translated. (The manifest keeps entries for everything, but only images present in the SEP render output are re-imported.)
  3. Create an SEP project on that folder (New Project → SEP, pick the _unreal_img folder), translate the images with SEP's OCR + editor, and export SEP's rendered images to a folder of your choice. Rendered files must keep the original file names and pixel dimensions.
  4. Insert translated images. Back on the SLRUnreal slide, fill the four folders (game, extracted-images folder, SEP render output, output folder) and run Insert translated images. The tool re-encodes every rendered PNG into the original texture's format (including its mip chain), rebuilds the affected containers, and writes them game-relative into the output folder. Copy those over a copy of the game.
Sizes are strict: a rendered image whose dimensions differ from the extracted one is rejected with a named error — resize it to the original size and run the insert again. Images whose pixel format cannot be re-encoded (float/HDR formats) and engine-internal virtual textures are skipped at extraction and reported in the console.

Demosaic (image-overlay material swap)

Demosaic is a standalone operation (since Phase 8b — it is no longer an export-dialog option). With an SLRUnreal project open, New Project → SLRUnreal → Demosaic (standalone): pick an output folder and the tool builds its own demosaic patch container (<name>_SLRDM_P.*) from the project's staging set — portable like the translation export, and deliberately named apart so both patches can sit in Paks/ at once. The candidate list is per-game and automatic; the summary reports applied and skipped candidates with reasons.

  • SampleGameA: 7 character models bind the overlay material on exactly one slot each; all 7 have clean materials in the same package and are swapped automatically.
  • SampleGameB: one wired event-image reference is swapped to its clean sibling (experimental — the display path is not traced end-to-end).
What demosaic cannot do: images with the overlay baked into the pixels (drawn and saved that way) cannot be revealed — the clean image no longer exists anywhere in the game. This affects most of SampleGameB's event CG. The exporter only touches material/reference bindings; it never invents image content.

Fonts — why English overflows, and what the swap does

Japanese UE games draw their text through a Japanese font, and Japanese fonts draw Latin letters wide (often full-width). Your English translations then overflow their UI boxes and wrap mid-word. Ticking Replace game fonts swaps the game's font files for SLR Translator's own faces, in two roles:

  • Dialogue/Japanese role — SLRCondensedCJK (the face SEP already uses for rendering): its Latin glyphs are narrow, so English text fits like it would in a Western font, and it still carries CJK coverage, so every string you did not translate keeps rendering in Japanese — no tofu boxes. This role covers the game's own font faces (SampleGameA's MS Gothic, SampleGameB's M PLUS Rounded 1c) and the engine's CJK fallback face (DroidSansFallback), which is what keeps untranslated Japanese safe even when a widget renders through the engine's fallback chain.
  • UI/Latin role — Stint Ultra Condensed: a narrower Latin-only face for menus, buttons and labels. Pure UI text never needs Japanese glyphs, and the narrow face fits translated English best. This role covers the engine's default faces (the Roboto family and the mono face).

Two Custom font fields below the checkbox accept your own .ttf/.otf/.ttc for each role (with a Browse… button each); your choices are remembered for the next export. Putting the same font in both fields forces one font everywhere. If a resolved font file is missing, the console logs a WARNING line and only the font stage is skipped — strings and images are still patched.

On Unreal Engine this swap is a data-only replacement: the game's fonts ship as packaged font files (.ufont) next to their font assets, and the game rasterizes its text from those files at runtime — there are no frozen glyph atlases to re-bake (the Unreal analog of Unity's TextMeshPro work). The font assets keep their names and references, so the game keeps using "its" fonts; they just contain SLR's faces. Nothing is added to the game and no game file is renamed.

Where the option lives: the Replace game fonts checkbox in the export dialog (strings flow) and the checkbox in the Insert translated images section (image flow). In both flows the font files join the same single container rebuild as the patches — one pass, no double rebuild. Ticking the box also makes an export with zero translated rows valid, so you can produce a fonts-only patch; export again with the box off to revert.

Text-box sizing: Unreal's UMG text blocks auto-size to their content (width comes from the layout slot, height grows with wrapping) — there is no per-widget size table to recalibrate the way fixed-layout engines sometimes need. The narrow fonts are the calibration: they are chosen so translated English fits the space the Japanese original occupied. If a specific game still clips a particular label, pick an even narrower face in the custom UI-font field.

Honest caveats: some games pin a specific sub-face inside a font collection (.ttc); when the replacement has a single face, the engine falls back along its font chain for such references — text stays readable (and Japanese still renders), but may appear in the fallback face. Sidecar files whose layout the addon does not recognize (e.g. compressed font packages in a future engine build) are skipped with a console line and keep their original look. Both reference games are validated: all 8 of each game's font files swap cleanly.

Known limits

  • Text inside compiled UI scripts (blueprint bytecode — SampleGameB's quest dialogue boxes, menu labels, guild scenes; SampleGameA's save messages and status titles) is extracted and patched with a same-size in-place method. A translation longer than the original's script slot is skipped with a reported reason (shorter or pure-ASCII translations always fit); string literals in the scripts that carry no localization key are left alone.
  • Games that derive their pak key at runtime (obfuscated, not hardcoded) defeat the offline key scan — enter the key manually when SLR reports a "key required" error (community key lists carry them); it is cached like a discovered one.
  • Float/HDR texture formats (PF_FloatRGBA and friends — effect flipbooks, never text carriers) and engine-internal virtual textures are not extractable; they are skipped and reported. The image round-trip has been validated on both reference games: SampleGameA (IoStore) and SampleGameB (pak).
  • Font replacement swaps the packaged font files (.ufont) it recognizes; compressed or future font-package layouts are skipped with a console line, and a game that pins a sub-face inside a font collection may show the engine's fallback face for those references (see Fonts).
  • One engine has been validated end-to-end per container kind: SampleGameA (IoStore) and SampleGameB (pak) are the reference games; other UE games should work but are untested.
